yt2txt/

Paste a YouTube link, get the meat of the video as structured Markdown. A React SPA on CloudFront talking to exactly one AWS Lambda, which hands the URL straight to Gemini and files the result in DynamoDB. Underneath the small surface area is a resumable job runner, a hand-written service worker, and a set of design decisions that only make sense once you know which limits they were bending around.

Architecture

The shape of it

Three layers, each with a single source of truth, and no framework doing the joining. There is no router, no state library, no API gateway, and no build step for the service worker.

LayerLives inWhat it is
Frontend src/ One App.jsx component holding five routes, plus a People.jsx page. Routing is 27 lines of useSyncExternalStore over the History API.
PWA public/ Hand-written sw.js, a manifest declaring an Android share target, and a bookmarklet for desktop browsers that have no share menu.
Backend backend/summarise/ One Lambda behind a Function URL, dispatched by HTTP method and by three magic keys on directly-invoked events.
Infra infra/pulumi/ 224 lines of Python Pulumi: S3 + CloudFront + ACM + Route53, three DynamoDB tables, the Lambda, its Function URL, and one EventBridge tick.

Everything is driven through make, which shells out to docker compose — you need neither Node nor Python on the host. There is no make test and no linter.

Runtime

Three flows

Summarise one video

The common path. Everything after the Lambda receives the URL is a straight line — Gemini fetches the transcript itself from the URL, so there is no transcript service and no media handling in this codebase at all.

01 canonicalise Browser rewrites shorts/live/embed/m. links to watch?v= and strips ?si= tracking.
02 dedupe Lambda reads DynamoDB by URL. A hit returns immediately with cached: true.
03 generate Walks a model chain, passing the URL as a fileData part with a duration-derived fps.
04 tag Parses and strips the Speakers: trailer line; falls back to a cheap text-only re-read.
05 persist Conditional PutItem. The loser of a race re-reads and returns the winner's row.

Share into the app

The manifest registers a share target posting to /share by GET, so Android hands the link over as a plain navigation with no server round-trip. The SPA reads the query string, scans url then text then title for the first YouTube link (different apps put it in different fields, often wrapped in prose), summarises with Flash Latest, and does a replacing navigation to the result so Back does not re-fire the share. On macOS and Linux this can never work — those OSes expose no share mechanism to Chrome — hence the bookmarklet on the Home page hitting the same /share?url= route.

Research a person

The most interesting machinery in the repo, and the one thing that is genuinely hard. A job searches the last six months of YouTube for a name, then summarises up to eight videos one at a time. Each video costs a real generateContent call, so the whole job can easily outlive a single Lambda invocation — even one with the maximum 900 s timeout.

The runner is idempotent and chunked. Before each video it asks context.getRemainingTimeInMillis() whether there is room; if not, it self-invokes a continuation and returns. Per-video rows persist as they complete, so a resumed run only picks up what is still pending. Three separate triggers call the same function:

  • the initial POST { action: "research" },
  • its own time-budget continuations,
  • and an EventBridge tick that scans for jobs idle past a 10-minute stall threshold and restarts them — recovering work whose Lambda was killed outright.

Status runs queued → running → finalising → done | error, with a continuation budget of 12 as a loop guard.

Data

Where state lives

TableKeyHolds
yt2txt-summaries url One row per summarised video: markdown, the model's own plain-English title, date, which model actually produced it, plus the authoritative YouTube video/channel titles and speaker tags.
yt2txt-people person Job state, progress, continuation count, last-progress timestamp, and the synthesised meta-summary.
yt2txt-people-videos person + videoId One row per video in a person's job, with its own status so runs resume rather than restart.

The four newest summary fields — videoTitle, channelTitle, channelId, speakers — are all best-effort, and rows written before they existed read back as null or []. A one-shot backfill.js enriches those rows, and is idempotent by construction: a row is done once it carries the attribute, and a failed extraction deliberately writes nothing so it stays eligible for a retry.

Worth knowing: listSummaries() whitelists fields by destructuring the DynamoDB item. Add an attribute and it is silently dropped from the list response until you add it there and to summaryPayload().

Rationale

Why it looks like this

Most of the odd-looking choices are load-bearing. This is the ledger of limits the design is bending around — read it before changing anything in the next section.

Function URL, not API Gateway
API Gateway caps at 29 s. Summarising a long video routinely takes longer, so the Lambda is exposed directly.
Permission before FunctionUrl
If the NONE-auth permission does not exist first, AWS caches a "no public access" authz state that survives later policy edits. The depends_on enforcing this is not decoration.
Throttled video tokens
Gemini defaults to 1 fps at full resolution, roughly 300 tokens/sec. A 25-minute video alone blows the 250k free-tier TPM limit. Hence MEDIA_RESOLUTION_LOW plus an fps ladder from 1.0 down to 0.1 by duration. Audio stays at 1-second granularity regardless, which is what timestamps anchor to.
Speaker tags as a prompt contract
Not responseSchema — the model chain falls back to Gemma, which does not support it. So the prompt asks for a trailer line, which is parsed and then stripped before storage.
Synchronous Gemini, not the Batch API
The Batch API is paid-tier only; on a free-tier key ai.batches.create() fails 400 FAILED_PRECONDITION.
Dynamic model list
Derived from ai.models.list() and cached 24 h. The same list backs both the dropdown and the request allow-list, so the two cannot drift. Hand-kept fallbacks exist only for when that fetch fails.
manifest.json, not .webmanifest
aws s3 sync picks Content-Type from the extension, and .webmanifest is not in the AWS CLI mime map — it would upload as application/octet-stream.
Never set Vite base: './'
Client-side routing depends on CloudFront mapping 403/404 to index.html and on Vite emitting absolute asset paths. Relative paths would break every non-root URL.
Self-invoke via env, not config
The worker reads AWS_LAMBDA_FUNCTION_NAME, injected by the runtime. Passing it as Pulumi config would be a circular dependency.

Proposals

What I would clean up, in order

Ranked by payoff per unit of effort, not by size — the numbering is the ranking. Two of these are correctness bugs that will bite as the table grows; the rest are duplication and structure. Every claim below points at the code it came from.

01

Run the tests that already exist

Confidence Effort: XS
Today

Four .test.mjs files — src/share.test.mjs, tags.test.mjs, people-pure.test.mjs, media-pure.test.mjs — each with a hand-rolled check() helper and a console.log('ok - …'). Nothing runs them. CI runs no tests at all.

Node 20 ships a test runner. Adopting it costs zero dependencies and turns four orphaned files into a gate: 

test:  ## Run pure-module smoke tests
	docker compose run --rm node node --test

Pass no paths. Bare node --test walks the working directory recursively, picks up anything matching *.test.mjs, and skips node_modules on its own — which is what finds all four files across src/ and backend/summarise/ in one run. Naming the two directories as arguments does not do this: the runner treats each path as a test module and tries to import it, so both fail and nothing runs. Explicit globs (src/*.test.mjs backend/summarise/*.test.mjs) work too, at the cost of needing an edit every time a file lands somewhere new.

Convert the check() calls to test() from node:test — the assertions are already node:assert/strict, so the bodies are unchanged — and add the step to both workflows. Do this one first; it is what makes the rest of the list safe to attempt.

02

History is an unordered Scan pretending to be a feed

Correctness Effort: M
Today

handler.js:316 — Scan({ Limit: 100 }), then sort by createdAt, then slice(0, 50).

DynamoDB's Limit caps items evaluated, and Scan returns them in internal hash order with no ordering guarantee. There is no LastEvaluatedKey follow-up here. So the moment the table passes 100 rows, "the last 50 summaries" becomes an arbitrary 100 rows sorted among themselves — and a brand-new summary can be absent from History entirely, depending on where its URL hashes. It will look like a caching bug and it is not.

Fix it with a global secondary index carrying a constant partition key and createdAt as the sort key, then Query it backwards: 

QueryCommand({
  IndexName: "byCreatedAt",
  KeyConditionExpression: "#pk = :all",
  ExpressionAttributeValues: { ":all": "SUMMARY" },
  ScanIndexForward: false,
  Limit: 50,
})

A single hot partition is entirely fine at this scale, and the write path already builds the item in one place, so stamping the constant on new writes is a one-line change.

Backfill before you cut over. A GSI is sparse: items missing its partition key are simply absent from the index. Every existing row predates the attribute, so a Query against the fresh index returns only rows written after the deploy — History would read as empty and then refill one summary at a time, which looks far worse than the bug being fixed. Stamp the attribute on writes first, run a one-shot pass over the table to add it to existing rows, confirm the index item count has caught up, and only then point listSummaries() at the Query. If you would rather not gate the cutover on the backfill, dual-read for one deploy: Query the index, and fall back to the current Scan when it returns fewer than expected. backfill.js is a working template for the one-shot pass.

listPeople() and resumeStalledJobs() also Scan — those tables stay small enough that it is defensible, but they deserve a comment saying so.

03

Add a single-summary endpoint; stop shipping the archive on every load

Correctness Payload Effort: S
Today

There is no way to fetch one summary. App.jsx:107 resolves /summary/<videoId> by searching the in-memory history array, which is populated by the one list call on mount.

Two consequences follow from the same root cause:

  • Deep links expire. Once a summary falls out of the newest 50, its permalink renders "Summary not found" — even though the row is right there in DynamoDB.
  • Every cold load pays for the archive. The list ships up to 8,000 characters of markdown per row across 50 rows — up to ~400 KB — so the detail page can read item.summary locally. The list UI itself uses 200 characters of it.

Add GET ?video=<id> returning one row, have the detail route fetch it when the item is not already in memory, and cut the list's markdown slice to ~300 characters. That is a smaller diff than it sounds — summaryPayload() already exists and already backs three response paths.

04

One copy of the model-call loop

Duplication Effort: S
Today

Four things exist twice, and the code says so out loud — handler.js:118 is commented "Copy of people.js's predicate":

isRetryableModelError (handler.js:120 / people-pure.js:53) · buildModelChain (handler.js:134 / people-pure.js:45) · MAX_MODEL_ATTEMPTS = 4 in both · withTimeout (people.js:76 / speakers.js:26).

The two predicates have already diverged: the people-side one also matches "timed out" and "timeout", because that path wraps calls in a timeout and the request path does not. That divergence is correct today and invisible tomorrow.

Extract one gemini.js with a single generateWithFallback(ai, { contents, chain, config, retries, timeoutMs }). Both callers do the same walk — try model, classify the error, advance — and the only real difference is that the people path adds exponential backoff between attempts, which becomes retries: 3 versus retries: 1. Keep the shared predicate in people-pure.js (the strictly broader one) and delete the handler's copy; it is already the dependency-free module that plain node can import.

05

Break up App.jsx — and hoist the components out of it

React footgun Structure Effort: M
Today

585 lines holding five routes, and Header (App.jsx:301) and SpeakerTags (App.jsx:275) are both declared inside the BrightBlogApp function body.

That last part is a real bug, not a style note. A component declared inside a render is a new component type on every render, so React unmounts and remounts its entire subtree each time — discarding DOM state and focus rather than reconciling. It is currently harmless only because neither subtree holds state. Move both to module scope, or to their own files, and pass what they need as props.

Alongside that split, three pieces are duplicated verbatim between App.jsx and People.jsx: the LAMBDA_URL/authHeaders pair (App.jsx:7 / People.jsx:4), the markdown urlTransform, and the markdown link component. A single src/api.js exporting typed calls — listSummaries(), getSummary(id), createSummary(url, model), listModels(), researchPerson(name) — plus a src/components/Markdown.jsx removes all of it and puts every fetch in the codebase in one file.

Two more things to sweep up in the same pass: replace the three alert() calls (App.jsx:178, People.jsx:80, People.jsx:99) with inline error state — the share panel already models this well — and key the history lists by item.url rather than array index (App.jsx:465, App.jsx:559), since new summaries are prepended and shift every index by one.

06

Set Cache-Control explicitly on deploy

Delivery Effort: XS
Today

Makefile:109 and deploy-site.yml both run a bare aws s3 sync dist/ s3://$BUCKET --delete. No object gets a Cache-Control header, so every file falls to CloudFront's default TTL and the browser heuristic.

That flattens a distinction the app depends on. Assets under /assets/ are content-hashed and immutable — they should be cached for a year. But sw.js and index.html must revalidate, and the documented way to push an update to every client is "bump VERSION in sw.js". If a browser is holding a heuristically-cached service worker, that bump does not land promptly. 

aws s3 sync dist/ s3://$BUCKET --delete \
  --cache-control 'public,max-age=31536000,immutable' \
  --exclude '*' --include 'assets/*'

aws s3 sync dist/ s3://$BUCKET --delete \
  --cache-control 'no-cache' \
  --exclude 'assets/*'

The CloudFront invalidation stays — it is what makes no-cache at the edge take effect immediately.

07

Key summaries on videoId, and share the canonicaliser

Data model Effort: M
Today

The hash key is the raw URL, and the Lambda's YOUTUBE_URL_RE accepts both watch?v= and youtu.be forms. So one video can hold two rows. backfill.js:52 works around exactly this, grouping rows by extracted video id because "the same video can legitimately hold several rows".

Canonicalisation happens in the browser (share.js:70), which means anything hitting the Function URL directly bypasses it.

src/share.js is already pure and dependency-free — the header comment says so and there is a plain-node test to prove it. Move it to a shared location, import it on both sides, canonicalise at the top of the Lambda's POST handler, and key the table on the 11-character video id. That collapses a whole class of duplicate-row bug, makes /summary/<videoId> a genuine key lookup rather than a client-side scan, and lets videoIdFromUrl (App.jsx:61) — the third id extractor in the repo, after videoIdFrom and extractVideoId — be deleted.

This one needs a migration: write new rows under the id, read through to the URL key on miss, then run a one-shot copy. backfill.js is a working template for exactly that shape of job.

08

Split the web Lambda from the worker Lambda

Blast radius Effort: L
Today

One function, timeout=900, serving both a public HTTP endpoint and three internally-invoked job types dispatched on magic keys — __personJob, __backfill, __resumeJobs (handler.js:336).

The two workloads want opposite settings. A GET / wants a short timeout, no self-invoke permission, and read-only DynamoDB access. The worker wants 900 s, lambda:InvokeFunction on itself, and write access to all three tables. Today the public endpoint carries the worker's IAM role and the worker's timeout, so a hung request can sit there for fifteen minutes.

Split them: web.handler behind the Function URL, worker.handler for EventBridge and self-invokes, sharing the same code bundle and the same modules. Two aws.lambda_.Function resources over one archive, two roles, and the magic-key branch disappears from the request path entirely. The Pulumi change is small — the archive helper already exists.

The further step, if the job runner ever gets harder: move the continuation loop to Step Functions, which gives retries, timeouts, and per-step observability for free and deletes the self-invoke plumbing, the continuation budget, and the stall-detection tick. That is a genuine rewrite of people.js, so it is worth it only if the current machinery starts failing in ways the logs cannot explain.

09

Drop Tailwind

Dead weight Effort: XS
Today

tailwindcss, postcss and autoprefixer are installed and configured, index.css:1 pulls in all three directives — and not one Tailwind utility class appears in any JSX. All 669 lines of styling are hand-written CSS with custom properties and BEM-ish class names.

The only thing Tailwind contributes is Preflight, which is stacked on top of the file's own hand-written reset a few lines below it. Deleting the three directives, tailwind.config.js, postcss.config.js and the three devDependencies removes a build step and a source of confusion about which reset wins, at the cost of a short explicit reset the file half-contains already. The CSS itself is good and stays exactly as it is.

Loose ends

Restraint

Things that look wrong and are not

A cleanup pass is where good constraints get optimised away. These four all read as obvious improvements and all of them would break something:

"Batch the Gemini calls"
The Batch API is paid-tier only. On this key it fails outright. The per-video synchronous loop is deliberate.
"Summarise videos in parallel"
Eight concurrent video calls against a 250k TPM free-tier limit would rate-limit the whole job. One at a time is the constraint talking.
"Use responseSchema for speaker tags"
Gemma does not support it, and Gemma is in the fallback chain. The prompt contract plus a text-only re-read is the version that survives the fallback.
"Replace sw.js with vite-plugin-pwa"
The hand-written worker has no precache manifest to keep in sync, because Vite's hashed filenames make the caching rules derivable at request time. The plugin would add a build step to solve a problem this app does not have.

Suggested order

Proposal 01 first — it is an hour, and it is what makes 02 through 07 verifiable rather than hopeful. Then 02 and 03 together, since they touch the same two functions and together fix both "new summaries sometimes vanish" and "old permalinks die" — budget for 02's backfill, which is the part that decides when the cutover is safe. 04, 06 and 09 are independent and can go in any order or any spare afternoon. Leave 07 and 08 until the first three have settled; both involve migrations, and neither is urgent.
